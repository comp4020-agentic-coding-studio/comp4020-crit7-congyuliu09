# Crit 7 reflection

**The breakthrough that moved the work forward** 
was reducing the project to one complete booking flow instead of trying to recreate a whole ANU room-booking platform. Early on, I realised that adding login, accounts and session management would create a lot of extra work without really helping me demonstrate the main full-stack ideas for this crit. I therefore kept Student ID as the lightweight identifier for creating, viewing and cancelling bookings. That decision made the rest of the system much clearer: first define the schema, then create bookings, then persist and retrieve them, then add cancellation and finally polish the interface. Keeping the scope small made it possible to finish each stage properly, test it, and commit it before moving on.

**What this changed about how I want to work as a developer** 
is that I now see more value in defining the boundaries of a system before asking an agent to implement it. Instead of starting with “build the feature,” I asked the agent to inspect the existing starter, keep the course stack, propose a minimal data model and explain how each stage would satisfy the spec. That made it much easier to notice problems as the project evolved. For example, the booking success redirect originally pointed back to `/`, which made sense before the My Bookings page existed, but became outdated once that page was added. Because the work was split into small stages and reviewed after each one, I caught and corrected that behaviour immediately. The main lesson I am taking from this crit is to work in a tighter cycle: define the scope, build one meaningful stage, verify it, reflect on what changed, and only then continue.
